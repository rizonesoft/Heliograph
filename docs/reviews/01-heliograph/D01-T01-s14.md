## Writer note: redesign after a gap reopened twice (session heartbeats)

Reconciliations 1 to 6 each reopened the same in-scope gap: a heartbeat that was on disk when a lookup started was missed while the session refreshed in another repository (eviction, interrupted refresh, concurrent supersede, read error during migration, sweep during enumeration, readdir ordering). Every case came from one mechanism: a named session kept one record outside any repository that moved from repository to repository, and each refresh had to copy the record it superseded into a per-repository key before removing it, so readers could fall into that hand-over. Per the gap-reopened-twice rule the patches stop and the mechanism is replaced (writer: claude, 2026-11-26).

- One key holds one heartbeat: `<lane>+r<32-hex sha256 of the session>+<repository>` for a named session in a repository, `<lane>+<hex>` for a named session outside one, `<lane>++<repository>` or `<lane>` for a sessionless lane. `place_hello` writes only its own key and never copies, moves, supersedes or removes another key, so no hand-over exists for a reader to fall into. Inside one key the stamped §4 generation chain is unchanged.
- Readers take the newest across the keys they need: `place_session_repo` reads the repository key and what an older build recorded for that repository under the key outside a repository; `place_session` takes the newest over the session's key outside a repository and all its repository keys; the bulk lookup behind `place_busy` and sessionless liveness gives every key as the heartbeat it holds. Records older builds wrote (`repository:` and `repo-time:` lines) are read where they lie and never rewritten, which also removes the upgrade migration.
- A call that names no agent keeps the agent the session last gave, read from its newest record (a name only; no heartbeat moves).
- Class regression: `RepositoryRouting.test_a_refresh_never_touches_another_key_so_no_lookup_loses_a_heartbeat` asserts that refreshes in four repositories leave every other key's file present and byte-identical, then sends unowned paths in repo-a while the session churns through repo-b, repo-c and repo-d for six seconds and requires every one to stay in repo-a. Against the previous `engine/place.c` it fails: `a refresh in repo-b changed os+dev+77...`.
- The §4 within-key contention test (`Sessions.test_concurrent_ordinary_refresh_never_erases_hello_metadata`) now contends inside one repository key, since writers in two repositories no longer share a key.
